🔍 How a Scan Works — Step by Step

POST /api/scans/analyze  (multipart/form-data)
  ├─ image file → saved to /uploads/ (UUID filename)
  ├─ productId  → selects OCR text fixture
  └─ packageHeightMm + packageWidthMm → font calibration

Step 1: DeclarationExtractor.extract(rawOcrText)
  Regex patterns → manufacturer, net_quantity, mrp,
                   mfg_date, consumer_care, unit_sale_price

Step 2: FontAnalyzer.analyze(calibration)
  estimatedMm = (packageHeightMm / imageHeightPx) × charHeightPx
  Compare to Rule 7/8 thresholds

Step 3: evaluateDeclarations(declarations, fontAnalysis)
  Each field → COMPLIANT / POTENTIAL_NON_COMPLIANCE / MANUAL_REVIEW

Step 4: Score Calculation
  score = (compliant + review×0.5) / total × 100
  ≥2 flags → capped at 65 | ≥3 flags → capped at 45

Results → SQLite (scans, declarations, ruleEvaluations, auditLogs)
       → JSON response → React renders compliance report

❓ Jury Q&A

Q1: "Why not use actual AI/ML for OCR?"
In the prototype, OCR is simulated with realistic text fixtures to demonstrate the full compliance pipeline reliably. In production, we integrate Google Cloud Vision API or AWS Textract — both return plain text OCR output that plugs directly into our DeclarationExtractor. The compliance engine is completely OCR-agnostic; it only needs raw text. This separation of concerns is by design.
Q2: "How does font size measurement work?"
It's basic photogrammetry. We know the physical package dimensions (e.g., 190mm × 120mm) from user input and image pixel dimensions. So: mm_per_pixel = packageHeightMm / imageHeightPx. Multiply by measured character height in pixels → real-world mm. Compare to Rule 7/8 schedule: 2mm min for 50g–200g, 4mm for up to 1kg, 6mm for above 1kg.
Q3: "Why SQLite? That's not production-grade."
Drizzle ORM makes it interchangeable — one environment variable DATABASE_URL switches the driver to PostgreSQL. SQLite is ideal for a hackathon prototype: zero infrastructure, instant startup, full SQL support. The schema and queries are identical; we don't use any SQLite-specific syntax.
Q4: "What's the legal basis for your three verdict states?"
This directly reflects the Legal Metrology Act, 2009. Section 18 makes non-compliance a cognizable offense, but formal adjudication requires a Weights & Measures Inspector. Our AI can only establish prima facie evidence. COMPLIANT (no action), POTENTIAL_NON_COMPLIANCE (flagged for review), MANUAL_REVIEW (borderline). Only the government officer can issue a 'Verified Violation' — reflecting the human-in-the-loop principle mandated by law.
Q5: "What happens when a consumer files a complaint?"
Complaint gets unique ID LM-2026-XXXXXX. Stored with scan ID, OCR findings, consumer location, purchase store. Company sees it with 48 hours to respond. If no response or rejected — auto-escalates to government verification queue. Officer marks "Verified Violation" → issues compounding notice under Section 36(1).
Q6: "How do you prevent false positives?"
Three ways: (1) Confidence scoring — anything below threshold → MANUAL_REVIEW, not auto-flagged. (2) Statutory disclaimer on every report — AI screening only, not a legal order. (3) Human-in-the-loop — no violation is legally actionable without officer verification. False positives burden companies, not consumers.
Q7: "Can this scale to crores of product scans?"
The compliance engine is a pure function — stateless, no I/O. Deployable as Lambda/Cloud Function horizontally. Fastify benchmarks at 70,000+ req/sec. Bottlenecks (database, OCR API) solved by PostgreSQL + connection pooling + OCR result caching by image hash. Architecture already has this separation ready.
Q8: "What's your USP over manual inspection?"
Manual inspection covers roughly 0.0001% of 10 billion+ packaged products sold annually in India. VidhiTrace enables 1.4 billion citizens to become the first line of compliance enforcement — every scan is evidence-backed, timestamped, and legally traceable. Manufacturers proactively fix labels. Officers focus on verified high-risk cases instead of routine screening.
Q9: "How do you handle rule version changes when DoCA amends rules?"
Version 2026.1 is captured in CURRENT_RULESET_VERSION constant and stamped on every scan record. Rules are in a typed array in rules/definitions.ts. When DoCA amends rules, we increment the version, modify definitions, and the Admin Rule Registry reflects it immediately. Historical scans retain their original rule version for audit integrity — non-repudiation by design.
Q10: "Is the data secure? What about consumer privacy?"
Uploaded images stored server-side with UUID filename — no PII in URL. Consumer passwords are bcrypt-hashed. Role-based access control — consumers can't see government workbenches and vice versa. Production additions: JWT auth, HTTPS, rate limiting, image expiry. Demo uses token auth for rapid iteration.
